# Global Discipline

## AGENTS.md resolution
- When creating or editing a file, check all folders in the relevant path for an `AGENTS.md`, which may have additional instructions specific to that folder
	- For example: If creating or editing `StreamActions.Twitch/Api/Games/Game.cs`, check for an `AGENTS.md` in: `StreamActions.Twitch`, `StreamActions.Twitch/Api`, and `StreamActions.Twitch/Api/Games`
- When multiple `AGENTS.md` contain conflicting instructions, the instruction in the most specific path should be used
	- For example: If creating or editing `StreamActions.Twitch/Api/Games/Game.cs` and it is found that `StreamActions.Twitch` and `StreamActions.Twitch/Api` have conflicting instructions in their `AGENTS.md`, the instruction in `StreamActions.Twitch/Api` should be used
	- Only the conflicting instructions should follow this rule, instructions which do not conflict should still be followed from the other `AGENTS.md` files in the path
- When reading and making use of a class/method from another file, do not read `AGENTS.md` from the path of that file, unless it is also in the path of the file being created or edited
	- For example: If creating or editing `StreamActions.Twitch/Api/Games/Game.cs`: do not check for an `AGENTS.md` in `StreamActions.Common` when using `Util.BuildUri`
	- For example: If creating or editing `StreamActions.Twitch/Api/Games/Game.cs`: do not check for an `AGENTS.md` in `StreamActions.Twitch/Api/Common` when using `TwitchSession.RequireUserToken`, but do use the `AGENTS.md` in `StreamActions.Twitch` and `StreamActions.Twitch/Api`, since they are still in the path of `Game.cs`
- The above rules may be overridden by an `AGENTS.md` file or the task prompt, when explicitly stated

## Repository-wide file rules
- After creating the first commit, all additional changes should be made as additional commits to the same branch
- Do not create `.gitkeep`
- Always include the license header, which may be found in `StreamActions.sln.licenseheader`
	- The license header format for different files is separated out into sections marked similarly to `extensions: .cs .js .css`, which indicates the list of file extensions that use the license header below that line
	- An empty line denotes the end of that license header
	- Some file types may require the license header to be placed on line 2 instead of line 1, such as `.sh` files. In this case, some license headers may or may not contain the required first line of the file, such as `#!/usr/bin/env bash`. If the license header does not contain the required first line of the file, add it before the license header. If the license header contains the required first line of the file, do not add it again
	- If the license header for a file extension is missing, return an error to the user requesting it
	- Exception: When writing files in the `.agents`, or `.github` folders, the license header is not required, unless otherwise specified
	- Exception: When writing the `README.md` file, the license should be written under the standard heading of the appropriate level, instead of using the commented out license header format, unless otherwise specified
	- Exception: When writing out `AGENTS.md`, `.gitignore`, `.editorconfig`, `.gitattributes`, or `.vsconfig`, the license header is not required, unless otherwise specified
- Remove all extra comments generated by you, which are not related to the documentation required by an `AGENTS.md` or task prompt
- Replace all curly apostrophes `’` with standard apostrophes `'` in comments and documentation, unless otherwise specified
- When resolving errors returned by GitHub Actions, always run your code review routine (to verify if changes are ready for PR/merge) after making changes to fix the errors
- Do not refactor, flag, or create tasks for functions/methods based on having "too many parameters", being "too long", or "too complex", unless otherwise specified
- Ignore parameter count limits during code reviews and task suggestions

## Context trust (no re-research)
- A Context Packet from the orchestrator, `flash-researcher`, or `triage-sweeper` is authoritative. Do not re-read files, re-fetch URLs, or re-run searches for facts it already contains
- Re-read only when one of these applies:
	- You are about to edit a file and need the exact current text. Read only the stated line range
	- A command result contradicts the packet
	- `git diff` shows that the file changed after the packet was written
- Glob-triggered rules (`10-csharp-dotnet.md`, `20-python-uv.md`) load automatically when matching files are touched. Reference them by filename in prompts; never paste their content
- Do not repeat verification that another agent reported as passing for unchanged files
- Read files with line ranges once the region of interest is known. Prefer `git grep -n` and `git ls-files` over recursive directory listings
- Stop as soon as the assigned question or task is complete

## Handoff formats
Every delegation and every report uses one of these formats. Keep reports under about 25 lines. Never paste full command output; quote only the relevant diagnostic lines.

### Context Packet (sent to an implementing or auditing agent)
```
GOAL: <one sentence>
ACCEPTANCE: <bullet criteria>
MODE: INTERACTIVE | SCHEDULED            (auditors only)
ATTEMPT: <n>/2                           (rapid-coder only)
FILES:
  EDIT: <absolute path> [Lx-Ly]
  REFERENCE: <absolute path> [Lx-Ly] - <why: pattern to mirror>
RULES: <AGENTS.md paths in scope> ; <.agents/rules files> ; <user overrides>
FACTS: <authoritative facts inline: API fields, types, scopes, signatures, status codes, source URL per fact>
VERIFY: <exact commands, or "skill dotnet-build-verify: <project> <files> <test project + filter>">
```

### Result Report (returned by any agent)
```
STATUS: DONE | BLOCKED | NEEDS_DECISION
CHANGED:
  - <path>: <one line>
VERIFIED:
  - <command>: PASS | FAIL
REMAINING: <diagnostic id + file:line, or "none">
NOTES: <at most 3 lines>
```

### Escalation Packet (appended to a BLOCKED Result Report)
```
SYMPTOM: <exact diagnostic / failing test / runtime error, with file:line>
ATTEMPTS:
  1. <change made> -> <result>
  2. <change made> -> <result>
HYPOTHESES: <ranked, with evidence>
SCOPE SIGNALS: <cross-project | async/concurrency | serialization | environment-dependent | unknown>
```
